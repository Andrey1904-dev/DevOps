## Архитектура

Существующий `web/app.js` используется обоими вариантами. При локальном запуске
`academy.py` обслуживает SQLite и API. Для Pages сборщик `scripts/build_pages.py`
подключает `cloud/config.js` и `cloud/client.js`: те же вызовы кабинета направляются
в Supabase RPC. `content.py` экспортируется в публичный `catalog.json`; идентификаторы
тем и уроков сохранены. Python на GitHub Pages не требуется.

Сборка не читает SQLite, локальные инструкции или аудит. `dist/` содержит только
index.html, app.js, style.css, client.js, config.js, catalog.json, .nojekyll, build.json.
CSS/JS подключаются относительно `./`, поэтому сайт работает в `/DevOps/`.
Маршрутизация использует hash; обновление страниц не требует SPA-rewrite сервера.

Publishable key в config.js намеренно публичный. Серверных ключей там нет.
REST-эквивалент SDK использует GoTrue Auth и PostgREST RPC по HTTPS. Никаких CDN,
библиотек из непроверенных URL, платных API или установки пакетов нет.

## Данные и доступ

Миграция: `supabase/migrations/202610230001_academy.sql`. Повторное применение
не удаляет данные. Она добавляет таблицы и заменяет только собственные функции:

| Таблица | Назначение |
|---|---|
| academy_profiles | Профиль, без дублирования email из Auth |
| academy_state | Каноническое состояние и монотонная revision |
| academy_diagnostic_attempts | Собственные диагностические ответы |
| academy_programs | 30 слотов, утверждение и дата |
| academy_lesson_progress | Статус, помощь, открытые подсказки |
| academy_attempts | Артефакт, объяснение и история попыток |
| academy_reviews | История подтверждённых внешних проверок |
| academy_repetition | Основания повторения и актуальность |
| academy_notes | Заметки с порядковым номером |
| academy_settings | Начальные настройки языка и темы |
| academy_events | Последовательная история действий |

Все таблицы имеют user_id с FK на auth.users и удалением CASCADE при намеренном
удалении аккаунта владельцем. В этом задании реальные аккаунты и данные не удаляются.
Составные ключи не позволяют пересекать владельцев. Для попыток есть индексы
по user_id/теме/дате. Связь проверки с конкретной попыткой определяется видом
проверки и стабильным ID; её формирование контролируется серверной функцией.

RLS включён на всех 11 таблицах: USING и WITH CHECK сравнивают auth.uid() с
user_id. Клиенту выдан только SELECT собственных строк. Прямые изменения таблиц
отозваны; запись идёт через academy_action, проверяющую владельца, revision,
аргументы и учебные переходы. У анонимного клиента нет доступа к личным данным
или RPC. SECURITY DEFINER имеет фиксированный пустой search_path и проверяет
auth.uid(); вспомогательные функции находятся в недоступной academy_private.

academy_load инициализирует только пустое состояние вошедшего пользователя и
возвращает его revision. academy_action блокирует строку владельца, проверяет
ожидаемую revision и атомарно обновляет состояние и нормализованные проекции.
Конфликт возвращается клиенту; автоматического повторного затирания нет.
Даты, ID, правила подсказок, утверждения и завершения задаёт PostgreSQL.
Подмена user_id отвергается. Принятый текст внешней проверки подтверждает сам
ученик; подлинность проверяющего не удостоверяется технически.

`202610230002_serialize_load.sql` также блокирует строку состояния при загрузке:
это не позволяет одновременной загрузке проецировать старый снимок поверх
более новой записи из другой вкладки. Миграция не удаляет и не пересоздаёт данные.
Экспорт всегда запрашивает актуальное состояние сервера; при отклонённом refresh
очищаются сессия, снимок и revision в памяти. Владелец дополнительно подтвердил,
что после обычной перезагрузки страницы кабинет остался открыт без повторного входа.

## Auth и первый вход

Для проекта настроены Site URL и разрешённый redirect:
https://andrey1904-dev.github.io/DevOps/

Публичная регистрация отключена отдельным разрешением владельца; подтверждение
email сохранено. Сторонние настройки SMTP, MFA и других сервисов не менялись.
Первый ученик должен быть реально приглашён владельцем, а не создан тестовыми
данными. Не публикуйте его email в исходниках или issue/PR.

1. Если приглашение ещё не отправлено: Supabase Dashboard → нужный проект →
   Authentication → Users → Add user → Send invitation. Используйте согласованный
   реальный email и не меняйте настройки других проектов.
2. Ученик открывает письмо и подтверждает вход самостоятельно.
3. Для дальнейших входов на сайте: email → получить ссылку → открыть в том же
   браузере. Запрос отправляет create_user=false и PKCE S256.
4. Существующий пароль поддерживается, но создание/сброс пароля приложение не делает.
5. Выход очищает локальную сессию; серверный отзыв выполняется через Auth. При
   сетевой ошибке приложение явно различает локальный выход и неподтверждённый отзыв.

Сессионные access/refresh токены хранятся в localStorage для восстановления входа;
это обычные пользовательские сессии, не административные ключи. На общей машине
выходите из аккаунта. CSP ограничивает скрипты своим origin, соединения — своим
origin и конкретным Supabase. Не храните секреты в ответах и заметках.
Вход по приглашению поддерживает implicit callback; токены удаляются из URL
до загрузки материалов. PKCE callback обменивает code с сохранённым verifier.

## GitHub и деплой

Пустой репозиторий сначала получил отдельный baseline существующего локального
MVP. Изменения Pages/Supabase идут в ветке feature/pages-supabase через PR.
История не переписывается; force push не применяется. Private-инструкции,
SQLite, .env, служебный config CLI и аудит игнорируются Git.

`.github/workflows/pages.yml`: PR выполняет только тесты и сборку с contents:read.
Push в main запускает сборку и отдельный deploy с pages:write и id-token:write.
Защиты веток не обходятся. Actions закреплены полными проверенными commit SHA;
checkout не сохраняет credentials. Privileged-триггеров и вставки входных данных
события в shell нет. Артефакт включает только dist/, а не весь репозиторий.

Проверка workflow при реализации: CRITICAL 0, HIGH 0, MEDIUM 0, LOW 0 найденных
проблем в перечисленных границах; это не гарантия отсутствия неизвестных проблем.

В целевом проекте с уже авторизованным CLI:

    supabase db query --linked --project-ref bkufrpbjgtpwtvutsvnh --file supabase/tests/isolation.sql --output json

Этот тест создаёт только две синтетические записи auth.users без email внутри
транзакции, проверяет роли anon/authenticated, собственные/чужие строки, подмену
user_id, запрет прямой записи, конфликт revision, подсказки и историю. Затем
ROLLBACK убирает только тестовую транзакцию; реальных аккаунтов и ответов не касается.
Это проверка SQL-контроля доступа, а не доказательство доставки письма и полноценного
входа с реальным JWT в браузере. Клиентские тесты используют моки, не тестовые аккаунты.

## SQLite и ограничения

При начале миграции SQLite проверена read-only: попыток, заметок, событий и
диагностических ответов нет; диагностика не начата, программа не утверждена.
Личные данные не выгружались в облако. Исходная SQLite остаётся локально.
Если в ней появятся реальные данные, перенос требует отдельного подтверждения,
резервной копии и проверки истории. Не выполняйте автоматический импорт.

Автоматических AI-вызовов, исполнения пользовательского кода, реальной Linux VM,
импорта JSON и редактирования уже утверждённого плана пока нет. Продвинутые темы —
слоты программы; стартовые лаборатории остаются текстовыми моделями Linux.
Диагностика и утверждение программы начинаются только решением самого ученика.
Фактические статусы Actions, Pages, приглашения, входа и браузерных проверок
должны фиксироваться отдельно: наличие файлов и мок-тесты не доказывают деплой/Auth.
